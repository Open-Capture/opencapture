# opencapture (OpenCapture) — Implementation Plan

**Status (2026-08-03): M0–M17 implemented and tested — full-page/visible/selected-area capture, annotation editor, popup state persistence, the OpenApps visual redesign, drag/text-tool fixes plus a Select tool, and a Firefox build target (`dist-firefox/`, same source tree) — minus Chrome Web Store/Edge Add-ons publishing automation, which needs real store credentials this environment doesn't have.**

Product: a privacy-first full-page screenshot browser extension — 100% local processing, no cloud upload. All capture/annotate/export features are free; the watermark tool is a paid Supporter feature (1000 credits, one-time, via openapps-gateway) added later, see the milestone entry for it below. Full design rationale (API choices, lazy-load/sticky-element/stitching/DPI handling, testing strategy, Rust-vs-TS split) is in this session's conversation history, not duplicated here; this file tracks what's actually built.

## Architecture

Rust does every pixel operation; TypeScript is the browser-API shell around it.

- **`crates/shot-core`** — pure, dependency-injected geometry and image pipeline: scroll-target planning, slice placement/cropping (device-pixel-exact, no gaps/overlaps by construction), PNG decode/stitch/encode (with `pHYs` DPI chunk), multi-page PDF export (`pdf-writer`), auto-split for oversized canvases. Compiles natively (tested via `cargo test` + `proptest`) and to `wasm32-unknown-unknown` (via `wasm-bindgen`, consumed by the extension's service worker).
- **`crates/shot-qa`** — native CLI for golden-assertion QA: PNG/PDF structural inspection, sha256 hashing, deterministic band-color sampling (for the ruler test pages), pixel-diff comparison. Used both by its own integration tests and by the Playwright e2e suite (spawned as a subprocess).
- **`apps/extension`** — MV3 extension shell (TypeScript, Vite). Background service worker orchestrates captures; content script (injected on-demand, never statically declared — see below) does DOM prep/scroll/pinned-element handling; popup UI triggers capture/export/copy.

## M0 — `shot-core`: plan/stitch/encode/pdf/wasm — **done**

- `plan.rs`: `scroll_targets` (coverage-complete scroll plan from page/viewport height) and `place_slices` (chains slices contiguously — cropping overlap from clamped/sub-pixel scroll positions rather than ever leaving a gap) and `split_ranges` (Chrome canvas-size-aware output splitting). All three proptested: tiling has no gap/overlap across arbitrary DPR/viewport/page-height/scroll-jitter combinations.
- `stitch.rs`: PNG→RGBA decode (RGB/RGBA/gray/gray-alpha normalized), width-mismatch detection (mid-capture page-resize abort signal), row-exact compositing into bounded-memory segments.
- `encode.rs`: deterministic PNG encoding (verified byte-identical for identical input — this is what lets the e2e/QA layer use exact assertions instead of fuzzy pixel-diff tolerances) with correct `pHYs` DPI chunk per DPR.
- `pdf.rs`: one PDF page per output image, sized in points to match CSS px (prints at 1:1 physical size), verified against `lopdf`-parsed output.
- `wasm.rs` (`cfg(target_arch = "wasm32")`-gated): `CaptureSession` (`pushSlice`/`finish`/`exportPdf`) — the entire extension-facing surface, all logic delegated to the modules above.
- 25 native tests (unit + proptest) green; clean `cargo clippy --workspace --all-targets` and `cargo fmt --check`; wasm32 build + `wasm-bindgen` glue generation verified working.

## M1 — `shot-qa` CLI — **done**

`png-info`, `pdf-info`, `hash`, `band-sample`, `diff`, `assert-absent`/`assert-present`. 7 integration tests (spawns the real compiled binary against generated fixtures, not just unit-level calls).

## M2 — MV3 extension shell — **done**

- **No static `content_scripts` entry and no `host_permissions`** — the manifest requests only `activeTab`/`scripting`/`downloads`/`offscreen`. The content script is injected on-demand via `chrome.scripting.executeScript` when a capture is triggered, so the extension has zero standing access to any page the user hasn't explicitly asked it to capture. (This was a mid-session self-correction — the first draft manifest had a static `<all_urls>` content script, which directly contradicted the "no site access until you click" trust-badge positioning from the design plan.)
- Content script (`content/index.ts`, deliberately zero-import — MV3 content scripts can't be ES modules): forces `loading="lazy"` images/iframes eager, does a priming scroll pass to trigger IntersectionObserver-based lazy loaders, waits for image decode + DOM-mutation quiet (bounded 8s), classifies `position: fixed`/`sticky` elements via `elementsFromPoint` sampling and hides them outside their "natural" slice (top-pinned shown only in slice 0, bottom-pinned only in the last slice).
- Background orchestrator: paces `chrome.tabs.captureVisibleTab` to the hard 2-calls/sec platform quota, drives the scroll/capture loop, feeds slices into the wasm `CaptureSession`, downloads PNG/PDF, copies to clipboard via a short-lived offscreen document (service workers have no `navigator.clipboard.write`).
- Popup UI: capture full page / capture visible / export PDF / copy to clipboard, with a live JSON capture report.
- Build pipeline: `cargo build --target wasm32-unknown-unknown` → `wasm-bindgen` → Vite bundles the glue via a **static** import (see bugs below) with `shot_core_bg.wasm` emitted as a normal Vite-hashed asset. `npm run build` is one command, clean from a fresh checkout.

## M3 — Fixed test pages + Playwright e2e — **done**

- `test-pages/`: `ruler-3000.html` (30 deterministically-colored 100px bands — the golden stitching test), `sticky-fixed.html` (fixed header/badge + sticky sub-header among non-colliding content bands), `lazy-native.html` (a verified-valid hand-generated 1×1 PNG data URI, scaled, `loading="lazy"`, 800px below the fold).
- `e2e/`: custom Playwright fixture (`launchPersistentContext` + `channel: 'chromium'` — see bugs below), a static file server for the test pages, and a test-only hook (`__OPENCAPTURE_E2E__`, a Vite `define`) that exposes `globalThis.__test.captureFullPage(tabId, windowId)` on the background service worker so Playwright can drive captures by explicit tab id — `activeTab`'s permission grant requires a real toolbar-icon click, which automation can't simulate, and this hook (plus a matching `<all_urls>` host-permission overlay, both gated on `OPENCAPTURE_E2E=1` and dead-code-eliminated / absent otherwise) sidesteps that without weakening the shipped manifest.
- **5/5 e2e tests pass against a real headless Chrome instance**, exercising the actual capture pipeline end-to-end (not mocked): service worker + wasm init; popup renders; full-page capture on the ruler page reproduces all 30 band colors at their exact expected rows (proves the scroll/capture/stitch pipeline is pixel-exact, not just structurally plausible); sticky/fixed elements appear once at the top and are absent from a mid-page sample (proves the pinned-element hide/show logic works against real Chrome layout, not just the content-script code compiling); the lazy image is confirmed loaded (non-placeholder pixel) at capture time.

**Three real bugs found only by actually running this in a browser** (all fixed, all now covered by the passing e2e suite so they can't silently regress):
1. `import()` is disallowed inside `ServiceWorkerGlobalScope` by the HTML spec (w3c/ServiceWorker#1356), regardless of `"type": "module"` — that only enables *static* import/export. The original design (dynamic-`import()` the wasm glue via `chrome.runtime.getURL`) doesn't work in a real MV3 service worker at all. Fixed by switching to a static import of the wasm-bindgen glue, letting Vite bundle it and rewrite the generated `new URL('shot_core_bg.wasm', import.meta.url)` into a proper hashed asset reference.
2. MV3's default extension CSP (`script-src 'self'`) blocks `WebAssembly.instantiate` entirely unless `'wasm-unsafe-eval'` is explicitly added — required manifest field, not optional, for any wasm-using extension.
3. Playwright's Chrome-extension-loading recipe requires the **literal** `channel: 'chromium'` launch option — not "omit channel" (defaults to a differently-behaving launch) and not `channel: 'chrome'` (real Chrome's plain `headless: true` is "old" headless, which has never supported loading extensions at all).

## M4 — selected-area capture, annotations, icons, CI — **done** (publishing automation not started)

- **Selected-area capture**: new `crop.rs` module in `shot-core` (`crop_rgba`, clamp-not-reject on out-of-bounds rects, proptested: never reads past source bounds) plus a `cropAndEncode` wasm export (decode → crop → re-encode, single-slice, no stitching plan needed). Content script shows a drag-to-select overlay (viewport-only, no scrolling — a scrollable-page selection tool is a distinct, more complex feature and out of scope here) and resolves with the CSS rect or `null` on Escape/too-small-drag. The cropped image is routed through a normal one-slice `CaptureSession` so `exportPdf`/clipboard-copy stay uniform across all three capture modes. 2 new e2e tests (pixel-exact crop dimensions/color; cancel-flow returns `null`), both passing against real Chrome.
- **Annotation editor**: new `apps/extension/src/editor/` page (opened in its own tab via `chrome.storage.session` handoff — the only `chrome.storage` area that accepts a raw `Uint8Array` via structured clone, no base64 round-trip needed). Pure TypeScript/canvas — arrow, rectangle, text, and blur (mosaic pixelation, block-average, genuinely irreversible — not a cosmetic CSS filter) tools, undo stack (image-snapshot based, capped at 20 steps), download. Deliberately **not** routed through `shot-core`: annotations are interactive UI, not something the test suite asserts geometric correctness on, which is the actual dividing line this project draws between Rust and TypeScript (see architecture section above) — contrast with crop/stitch, which *are* Rust because their results get pixel-exact-asserted. 1 new e2e test drives real mouse drags on the rendered canvas and verifies: the rectangle stroke lands where dragged, undo restores the exact prior pixels, and blur genuinely mixes two previously-distinct band colors into one (sampled one pixel on each side of an exact, deliberately-computed mosaic-block boundary — not a vague "did something change" check).
- **Icons**: `scripts/generate-icons.mjs` renders 16/48/128px PNGs from pure pixel math (no image library, no design tool) — a rounded-square accent-blue background with four white L-shaped corner brackets (standard "screenshot selection" iconography). Wired into `manifest.json`'s `action.default_icon` and top-level `icons`.
- **CI**: `.github/workflows/ci.yml` — lint (`fmt` + `clippy -D warnings`), `cargo test --workspace`, wasm build + extension typecheck/build (artifact-uploaded), and the full Playwright e2e suite against real headless Chrome, all on `ubuntu-latest`. Lives at `opencapture/.github/workflows/`, matching the exact convention `openframe` already established in this codebase (its own `Cargo.toml` `repository` field distinct from the root workspace's, structured as if it's — or will be — its own repository; GitHub Actions won't pick up a nested `.github/workflows/` from a nested-repo layout, so this only activates once/if `opencapture` is split out, same as `openframe`'s already does).
- **One real cross-cutting bug caught mid-implementation**: the first draft of `captureSelectedArea`'s report used sanity-check assumptions about mosaic block boundaries in the *e2e test* that turned out to be wrong twice in a row (first attempt sampled points 1px into the antialiased stroke edge rather than the solid stroke; second attempt sampled two points far enough apart to land in *different* mosaic blocks, which — for a genuinely-uniform underlying region — made pixelation a legitimate no-op and failed the test for the right code, wrong assertion). Fixed by sampling exactly on either side of a hand-computed block boundary. Worth remembering: pixelating a solid-color region is *correctly* a no-op; only a boundary-straddling sample proves the blur ran.

## M5 — crop-before-output, PNG/PDF format choice — **done**

- **Review-before-download flow**: `captureFullPage` (when it produces exactly one output image — the common case, well under the ~16000px stitched-height split threshold), `captureVisible`, and `captureSelectedArea` no longer download a PNG immediately. Instead `background/index.ts` now hands the image straight to the editor tab (`chrome.storage.session` `editorImage` + `editorDpr`) so the user can crop/annotate and explicitly pick a format before anything touches disk. A new `CaptureResult.openedEditor` field tells the popup which happened. **Very long pages that still split into multiple PNGs keep the old immediate-multi-file-download behavior** — cropping across split boundaries isn't well-defined, and "Export as PDF" (unchanged, still merges via `CaptureSession::exportPdf`) is the existing answer for "I want one file, not N," so this case was deliberately left alone rather than growing a second, more complex review path.
- **Crop tool** in the annotation editor: drag-to-select then release-to-commit, consistent with the existing arrow/rect/blur interaction pattern. Committing a crop actually **resizes the canvas element**, which broke the original undo stack (a bare `ImageData` snapshot can't tell `putImageData` to grow the canvas back — it silently clips instead). Fixed by giving every undo entry its own `{width, height, data}` — Undo now restores both the pixels and the canvas's prior dimensions. Opens as the default active tool (crop-first, since that's now the primary reason the editor auto-opens).
- **PNG/PDF format choice**: the editor's single "Download PNG" button became two — "Download PNG" (unchanged, `canvas.toBlob`) and "Download PDF" (new). PDF export needed a new Rust entry point since the existing `CaptureSession::exportPdf` only works from a live capture session's cached images, not an arbitrary (cropped/annotated) canvas: added `pngToPdf(png_bytes, dpr)` to `wasm.rs`, a thin wrapper around the already-tested `pdf::build_pdf` for a single image. The editor page now statically imports the wasm-bindgen glue directly (same static-import reasoning as `background/wasm-loader.ts`, though a normal extension page isn't actually bound by the service-worker dynamic-`import()` restriction — kept consistent anyway) and reads `editorDpr` from `chrome.storage.session` so the PDF page prints at the correct physical size.
- **Console warning fix**: Vite's auto-injected modulepreload polyfill (`<link rel="modulepreload">` + a polyfill script) is meaningless across an extension's isolated per-page JS worlds and was logging a "cross-world extension resource mismatch" warning in the popup. Fixed with `build.modulePreload: false` in `vite.config.ts` — every target browser (Chrome 116+) has native modulepreload support anyway.
- **New e2e coverage** (capture.spec.ts now 9/9, up from 8): crop resizes the canvas to exactly the dragged rect with pixel-accurate cropped content, undo-after-crop restores both the original canvas dimensions and pixels (not just clipped pixels at the wrong size), and both download buttons produce real files (PNG magic bytes; PDF starts with `%PDF-` and `shot-qa pdf-info` reports exactly 1 page) — driven through real `context.waitForEvent("download")` events, the first time this suite has exercised an actual download rather than just the in-memory image bytes. A second new test proves the `openedEditor` routing itself: calling the *exact* `handleRequest` the real `chrome.runtime.onMessage` listener calls (not the orchestrator-level `__test.*` hooks the rest of the suite uses, which bypass that branching logic entirely) confirms a capture opens an editor tab instead of downloading.
- **Testing gotcha worth remembering**: simulating "click the popup" by opening `popup.html` as a real Playwright tab and clicking a button in it doesn't work for anything that depends on `chrome.tabs.query({active:true})` — Chrome's real toolbar popup isn't a tab at all, but a Playwright-opened tab standing in for one *is*, and any trusted-input click on it (even a synthetic `.click()` via `evaluate()`, apparently) re-activates that tab and steals `activeTab`'s target away from the page actually being captured. `chrome.runtime.sendMessage` from the service worker to its own `onMessage` listener also silently fails ("Could not establish connection") — Chrome doesn't deliver a runtime message back to its own sending context. The fix that actually worked: extend the existing `__test` E2E hook to call `handleRequest(...)` directly from within the service worker's own script — same function the real listener calls, no second tab, no cross-context messaging needed.

## M6 — fix aggressive PNG splitting, adjustable crop — **done**

- **Raised the canvas split thresholds to match Chrome's real limits.** `MAX_CANVAS_AREA_PX` was 24M px — researched Chrome's actual 2D canvas ceiling (32,767px per dimension, 268,435,456px total area; exceeding either silently makes the canvas unusable) and found the area budget, not the dimension cap, was the binding constraint for ordinary pages at 2x+ device pixel ratio: at a typical 3024 device-px-wide Retina viewport, 24M px allowed only ~7936 device px (~3968 CSS px) of height before splitting — an entirely normal single-page article length, not an "extremely long page." That's what was producing "it only captured 2 screenshots" for pages that should have fit in one image. Raised to `MAX_CANVAS_DIMENSION_PX = 30_000` / `MAX_CANVAS_AREA_PX = 100_000_000`, both with a safety margin under Chrome's real limits (this also bounds the editor's on-screen `<canvas>`, a real DOM element genuinely subject to those limits, not just an in-memory RGBA buffer). `stitch.rs`'s split-focused unit test was rewritten to exercise the dimension bound with a narrow synthetic width (keeps the test's encoded buffer small) rather than the area bound, since reproducing an area-bound split at the new, much larger threshold would require an unrealistically large test buffer; the area-bound path stays covered independently by `plan.rs`'s `split_ranges` proptests, which don't need real pixel data.
- **Adjustable crop selection.** The crop tool previously committed to the canvas the instant the mouse button was released. Reworked into a two-phase interaction: releasing the initial drag now shows an adjustable marquee (dashed outline + 8 drag handles) instead of cropping immediately — the user can resize it via any handle, reposition it by dragging inside it, then explicitly commit ("Apply Crop" button or Enter) or discard it ("Cancel Crop" or Escape). Selecting a different tool, or clicking global Undo, cancels any pending crop first rather than leaving stale state behind.
- **Auto-scroll while cropping.** Screenshots are routinely taller than the editor window, so `#canvasWrap` (the scrollable container around the canvas) now auto-scrolls toward the cursor once it's within ~36px of the wrapper's edge, during any of the three crop drag modes (initial draw, handle-resize, marquee-move) — driven by a `requestAnimationFrame` loop rather than the `mousemove` event, since the cursor doesn't move (so fires no `mousemove`) while the page scrolls underneath a stationary mouse.
- **One real bug caught while wiring up the Apply/Cancel buttons**: setting `button.style.display = ""` to make them visible again silently did nothing, because the stylesheet already declares `#cropApply, #cropCancel { display: none; }` — an empty inline style removes the inline override and falls back to that same stylesheet rule, which still says `none`. An inline style only wins the cascade with an explicit value (`"inline-block"`), not by being merely present-but-empty. Worth remembering for any other toggle-visibility-via-inline-style code in this codebase.
- **New e2e coverage** (10/10, up from 9): the annotation-editor test now drags an initial crop rect, asserts the canvas is *not* resized yet and the Apply/Cancel buttons appear, resizes the pending selection via its bottom-right handle, and only then applies — asserting the *final* committed size reflects the adjustment, not the original drag. A new dedicated test captures a 3000px-tall page, opens the editor, starts a crop drag, holds the cursor near `#canvasWrap`'s bottom edge without further movement, and asserts `scrollTop` increases on its own — proving the rAF-driven auto-scroll loop is genuinely self-sustaining, not just responding to fresh mouse movement.

## M7 — rebrand to OpenCapture, save-location preferences — **done**

- **Rebrand**: renamed "LocalShot" → "OpenCapture" everywhere user-facing and internal — `manifest.json`'s `name`, popup/editor page titles and headings, downloaded-file prefixes (`opencapture*.png/pdf`), content-script internal style/attribute IDs, e2e temp-dir prefixes, and this plan/the testing guide. `apps/extension`'s npm package name was already `@opencapture/extension`, untouched. Icons (pixel content) weren't touched — no product name is rendered into them.
- **Save-location preferences**: a "Save to" section at the top of the popup, above the capture buttons, with two persisted text inputs — a folder and a filename. New `src/chrome/save-prefs.ts` (`getSavePrefs`/`setSavePrefs` backed by `chrome.storage.local`, plus `resolveDownloadPath(prefs, suffix, ext)` which sanitizes both fields and joins them into the value passed to `chrome.downloads.download`'s `filename` field) is used at every download call site: the multi-file long-page PNG split and "Export as PDF" in `background/index.ts`, and both "Download PNG"/"Download PDF" in the editor.
  - **Deliberately not a native folder-picker dialog.** Chrome extensions can't point `chrome.downloads.download`'s `filename` at an arbitrary absolute path anywhere on disk in the first place — it's always resolved relative to the browser's configured Downloads directory, so "select a preferred directory" concretely means a relative subfolder under Downloads, not a full filesystem browse. Even if it were possible, `showDirectoryPicker()` (File System Access API) needs a document context and reliably closes an extension's transient popup the instant the native OS dialog steals focus — a well-known MV3 popup gotcha — so a picker-based flow would need to live in its own persistent tab, not the popup the user asked for this to be in. Plain text inputs sidestep both constraints entirely.
- **Testing gotcha worth remembering:** verifying the downloaded file actually landed in the requested subfolder can't be done through Playwright's `Download` object *or* `chrome.downloads.search()` — Playwright's persistent context intercepts downloads at the CDP level and redirects them into its own artifacts directory for test hermeticity, and that redirection shows up in `chrome.downloads.search()`'s own `filename` record too, not just Playwright's side. The fix: stub `chrome.downloads.download` itself (in the page context that calls it) to capture its arguments and resolve without doing anything, then assert on what our code *passed* to it — the correctness that actually matters (did `resolveDownloadPath` compute the right value and did it reach the API call) is fully covered without needing a real download to complete at all.

## M8 — arbitrary-directory save via File System Access — **done**

- **A real "Browse…" folder picker, directly in the popup.** M7 shipped a text-based relative-subfolder-under-Downloads preference and explicitly scoped out a native picker because `chrome.downloads.download` can't point at an arbitrary absolute path and `showDirectoryPicker()` needs a document context — and the concern was that an MV3 popup doesn't survive an OS dialog taking focus. First implementation of this milestone routed the picker through a separate settings tab to sidestep that risk; per explicit direction, that indirection was removed — the popup's "Browse…" button now calls `showDirectoryPicker({mode:"readwrite"})` directly (`src/chrome/pick-directory.ts`), one click, no extra tab. The old relative-subfolder text input was also removed from the popup (redundant now that a real picker exists) — the "Filename" field is the only text input left; folder selection is Browse-or-nothing (defaults to the Downloads root).
- **Storage**: `chrome.storage` only holds JSON-serializable values, and a `FileSystemDirectoryHandle` isn't one — so the chosen handle is persisted via IndexedDB instead (`src/chrome/dir-handle-store.ts`), which the File System Access spec explicitly documents as structured-clone-compatible for this exact purpose.
- **Writing**: `src/chrome/fs-save.ts` wraps the actual write (`getFileHandle(name, {create:true})` → `createWritable()` → `write()` → `close()`) and a permission check/re-request (`queryPermission`/`requestPermission`, `mode:"readwrite"`) — the query never needs a gesture, but a *lapsed* grant's re-request does, which isn't available at capture time, so a lapsed permission is treated as "fall back," not an error.
- **Unified fallback**: `src/chrome/save.ts` (`saveOutput(bytes, suffix, ext, mime)`) is the single call site every download goes through — it tries the chosen directory handle first (if one is set and still granted) and falls back to the M7 relative-subfolder `chrome.downloads.download` path on *any* failure (permission lapsed, handle invalid, or — genuinely unverified in this sandboxed dev environment — File System Access writes not being supported from whatever execution context called it; see the honest limitation below). `save-prefs.ts` has `resolveFilename()` (just the sanitized `<base><suffix>.<ext>`, no folder) alongside `resolveDownloadPath()` (which also joins a relative subfolder — dormant now that there's no UI to set one, but still the correct fallback shape), since a direct filesystem write only needs the former — the folder there *is* the handle, not a path string.
- **TypeScript DOM lib gap**: `queryPermission`/`requestPermission` (the File System Access permissions extension) and `Window.showDirectoryPicker` aren't in the pinned TypeScript version's bundled `lib.dom.d.ts` — added a small ambient declaration file (`src/types/file-system-access.d.ts`) augmenting `FileSystemHandle`/`Window` via declaration merging rather than redeclaring the whole interface.
- **New e2e coverage** (12/12): clicking "Browse…" in the popup doesn't crash the page or persist a stale handle when the picker can't be shown (headless Chromium's ceiling — see below); the filename preference still applies correctly to downloads with the folder field gone.

**Honest limitation, stated plainly:** headless Chromium has no real OS folder dialog to show. In this environment, `showDirectoryPicker()` reliably auto-rejects with an `AbortError` (the same rejection path a real user cancelling produces, which `pick-directory.ts` already treats as a silent no-op) — meaning the actual "pick a real folder, then have a capture write into it" path has **not** been run end-to-end by this project's automated suite, unlike everything else documented in this file. Nor could it be, without a real Chrome window and a human at the OS dialog. Two things specifically need manual verification there: (1) whether a *real*, toolbar-anchored popup (not a regular tab, which is all Playwright can open — it can't simulate a toolbar-icon click to open a true anchored popup at all) survives long enough for `showDirectoryPicker()` to resolve, since MV3 popups are documented to close when a native OS dialog steals focus — if it doesn't survive, the settings-tab indirection this milestone removed would need to come back; (2) whether `FileSystemDirectoryHandle` writes work from a service worker (`background/index.ts`'s two direct-download paths — the multi-file long-page split and "Export as PDF") — `save.ts`'s try/catch degrades gracefully to the relative-subfolder fallback either way, but which path actually runs there in practice is unconfirmed. What *is* covered by the passing suite: the fallback path (no folder chosen) works exactly as before, the Browse button is wired up correctly, and the picker's rejection doesn't corrupt any state or crash the page.

## M9 — three user-reported bugs: clipboard size cap, no editor exit, editor zoom — **done**

- **"Copy to Clipboard" threw `Error: ... Message exceeded maximum allowed size of 64MiB`.** Root cause: `copyPngToClipboard()` sent the captured PNG's raw bytes as part of a `chrome.runtime.sendMessage` payload to the offscreen document (the only context with `navigator.clipboard.write`), and that API has a hard ~64MiB per-message cap — a large full-page capture's PNG can exceed it outright. Fixed with a new `src/chrome/blob-store.ts` (a small generic IndexedDB key/value byte store — shared across every extension context, since they're all the same `chrome-extension://<id>` origin, with no comparable size ceiling): the bytes go into IndexedDB first, and only a small "go read it" signal crosses `sendMessage`. Applied the identical fix to the editor-image handoff (`background/index.ts`'s `openEditorWithBytes` → `editor.ts`'s `loadImage`), which used `chrome.storage.session` — an *even smaller* 10MB default quota — for the same category of payload; not reported broken yet, but the same root cause and trivial to fix with the module already in hand.
- **No way to exit the editor.** It opens in its own tab with no close affordance. Added a "Close" button to the toolbar; closes via `chrome.tabs.getCurrent()` + `chrome.tabs.remove()` (not just `window.close()` alone, which can silently no-op for a tab this document didn't itself open via `window.open()` — which is exactly how the editor tab is created, via `chrome.tabs.create()` from the background service worker).
- **Editor appeared "zoomed in" and left-aligned, not full width.** The canvas rendered at its native pixel-buffer size with no CSS scaling — a capture at 2x+ device pixel ratio (the common case) is up to 2-3x the size it actually appeared on the original page, so it overflowed the window and (being left-aligned by default block layout) looked cut off rather than fitted. Fixed with `max-width:100%; height:auto; margin:0 auto` on `#canvas` (scales down to fit, preserves aspect ratio, centers — never scales *up* a naturally-small capture). This isn't just a CSS change: every mouse-to-canvas coordinate calculation (drag tools, crop handles, auto-scroll) previously assumed a 1:1 CSS-pixel-to-buffer-pixel mapping, which is no longer true once the canvas is genuinely scaled down — `canvasPoint()`/`pointFromClient()` now multiply by `canvas.width / renderedRect.width` to convert real mouse position into buffer-space coordinates, and the crop tool's resize-handle hit targets/drawn size scale by the same ratio so they stay a consistent ~10px on screen regardless of zoom level (otherwise they'd shrink to near-unclickable on a heavily-scaled-down capture).
- **A pre-existing latent bug surfaced while fixing the above**: `editor.html`'s `#canvasWrap` used a hardcoded `height: calc(100% - 52px)` guessing the toolbar's height — adding the Close button (or anything else that ever changes toolbar height, e.g. wrapping to a second line on a narrow window) silently pushes `#canvasWrap`'s box past the actual viewport bottom, since its height doesn't adapt. Replaced with a proper flex layout (`body{display:flex;flex-direction:column}`, toolbar `flex:0 0 auto`, canvasWrap `flex:1 1 auto`) that has no magic number to go stale.
- **New/updated e2e coverage** (15/15, up from 12): a dedicated test forces a capture wider than the editor window (2000px) to actually exercise the scaled-down path (every other test's captures happen to be narrower than the test window, so they'd pass even with the old, broken 1:1 assumption) — draws a rectangle via buffer-space-to-screen-space-converted coordinates and confirms the stroke lands exactly where the buffer-space math says it should. ## M10 — content-script re-injection SyntaxError, canvas readback perf hint — **done**

- **`Uncaught SyntaxError: Identifier '...' has already been declared` in the extension's error log.** Root cause: `content.js` has no static `content_scripts` manifest entry (deliberate — see the privacy-architecture note above), so it's injected fresh via `chrome.scripting.executeScript({target:{tabId}, files:["content.js"]})` on *every single capture*. `chrome.scripting.executeScript`'s isolated world persists across repeated injections into the same tab/frame — it's only torn down on navigation — so capturing the same tab twice without a reload in between (two clicks of any capture button, or "Capture Full Page" then "Capture Selected Area") re-runs the file's top-level `const`/`let` declarations into a scope that already has them from the first injection. This is *not* just a cosmetic logged warning: verified experimentally (reverted the fix, reproduced, then re-applied and reverified) that the second capture actually **hangs and times out** — the SyntaxError fires as an uncaught exception on the page (a `pageerror` event, not a rejected `executeScript()` promise and not a `console.error` call, which is why it's easy to misdiagnose as harmless). Fixed by wrapping the entire content script body in a re-injection guard (`if (!window.__opencaptureContentLoaded) { ...; window.__opencaptureContentLoaded = true; }`) — a second injection into an already-loaded tab is now a clean no-op, since the first injection's message listener is still alive in that persisted isolated world and keeps handling every subsequent capture correctly on its own.
- **Canvas2D `willReadFrequently` performance warning** in the editor — harmless but easy to fix: the editor's canvas does `getImageData()` readback on every drag-tool move, crop render, and blur, which Chrome recommends opting out of GPU-backed rendering for. Added `{willReadFrequently: true}` to the editor's `getContext("2d")` call.
- **New e2e coverage** (16/16, up from 15): captures the same tab twice back-to-back with no reload and asserts on a `pageerror` listener (not `console`, and not the capture's own report — both of those looked clean even with the bug present, which is exactly why this needed a `pageerror` listener specifically to catch it). Verified this test actually catches the regression by temporarily reverting the fix, confirming the test both reproduces the hang and fails, then re-applying the fix and reconfirming green — not just written and assumed correct.

## M11 — clipboard "Document is not focused" — **done**

- **Root cause, confirmed in real Chrome usage (not just this project's headless test harness, which is what M9 mistakenly assumed).** `navigator.clipboard.write()` — the modern async Clipboard API — requires the calling *document* to have real focus. Offscreen documents are invisible and structurally never become the focused document, so this call was **always** going to fail from `offscreen.ts`, regardless of how genuine the user's originating click was. M9's fix (moving the PNG bytes off the size-limited `sendMessage` payload) was necessary but not sufficient — it got the message *to* the clipboard API cleanly, but that API itself can't work from this context at all.
- **Fix**: `offscreen.ts` now tries `navigator.clipboard.write()` first, and on the specific "not focused" failure, falls back to the long-established pre-async-API workaround — select an `<img>` inside a hidden `contenteditable` element and run `document.execCommand("copy")`, which copies the actual selected image data to the system clipboard and has no focused-document requirement of its own.
- **Verified as far as this environment allows, and no further** — updated the M9 clipboard e2e test to confirm the fallback is actually *reached* (its own distinct failure — `execCommand('copy') returned false` — replaces the original "not focused" error). It still doesn't succeed in this harness, because there is no real user gesture anywhere in that specific test's call chain (it drives `handleRequest()` directly from the service worker, not via an actual click) — `execCommand` has its own transient-activation requirement that a fully synthetic call obviously can't satisfy. Getting a *reliably reproducing* Playwright test with a real click on a real popup button crashed the browser context outright in this environment (tooling instability, not a product bug — abandoned that path rather than sink further time chasing a harness artifact). **Whether the fix resolves the user's exact real-world case needs their own confirmation in real Chrome.**
- **Testing gotcha caught along the way**: while investigating, discovered that 5 separate editor-related e2e tests shared a subtly wrong wait condition — `waitForFunction(() => canvas.width > 0)` — which is satisfied by the browser's *default* un-initialized `<canvas>` size (300×150 per the HTML spec) before `loadImage()` ever runs, not just after. It happened not to matter in practice as long as the real image load consistently won the race against the next assertion, until a heavier-than-usual stretch of back-to-back test runs in this session tipped that race the other way and one test read the canvas mid-load (got `height: 150`, the default, instead of the expected `3000`). Fixed all 5 occurrences to check `(c.width !== 300 || c.height !== 150)` as well — an existing latent flakiness risk, not a new one introduced by this milestone, but only visibly manifested now.

## M12 — clipboard "execCommand returned false", blur/drag lag — **done**

- **The clipboard fallback failed too, in real Chrome.** M11's `document.execCommand("copy")` fallback (added because `navigator.clipboard.write()` can't work from an offscreen document) also failed — `execCommand('copy') returned false`. Root cause: `execCommand` has its own transient-user-activation requirement, same as the modern API, and activation doesn't transfer across documents via messaging — an offscreen document, having never itself received the real click, has none of its own no matter how recently the popup was clicked. **This proved the whole offscreen-document architecture for clipboard was wrong from the start**, not fixable by trying a third method in the same place. Real fix: do the clipboard write directly in `popup.ts`'s click handler — the one document that actually receives the real click, and so is the only place in this extension where both a real focused document and real transient activation are simultaneously available. `orchestrator.ts` now also stashes the last capture's first image in blob-store (`LAST_CAPTURE_BLOB_KEY`, persists across reads unlike the ephemeral `EDITOR_IMAGE_BLOB_KEY`) so the popup can read it directly, with no background round-trip. The offscreen document, `chrome/clipboard.ts`, the `"offscreen"` manifest permission, and `PopupRequest`'s `copyToClipboard` variant are all now dead code and were deleted rather than left stubbed out. New `src/chrome/copy-image.ts` holds the try-modern-API/fall-back-to-execCommand logic (the execCommand path still has legitimate value as a fallback — real Chrome versions/configurations can differ in `navigator.clipboard.write()` support even from a properly-focused document). **This one has real end-to-end proof, not just "doesn't hit the old error"**: a genuine Playwright `.click()` on the popup (a real tab, not an offscreen document) now produces an actual `"Copied to clipboard."` success via the primary API — the fallback wasn't even needed in testing.
- **Blur (and every other drag tool) was very laggy on a large capture.** Root cause: every drag tool did a full-canvas `getImageData()` snapshot on mousedown and a full-canvas `putImageData()` restore-then-redraw on **every mousemove** during the drag — for a large capture (a full-page screenshot can easily be tens of millions of pixels), that's a large pixel-copy operation happening dozens of times a second for the entire duration of a drag, regardless of how small the actual preview shape was. Fixed architecturally: live previews (arrow/rect/blur outline, crop marquee+handles) now draw on a separate, absolutely-positioned overlay canvas (`#previewCanvas` in `editor.html`) that exactly tracks the real canvas's rendered position/size (via `offsetLeft`/`offsetTop`/`clientWidth`/`clientHeight`, resynced after load/crop/undo/window-resize) — cleared and redrawn with cheap GPU-backed shape primitives (`clearRect`/`strokeRect`/etc.) on every mousemove, never touching the real canvas's pixel data at all. The real canvas is only read/written once, at the actual commit (mouseup, or Apply Crop) — this also simplified the code, since the crop tool's `cropBaseSnapshot` (previously restored on every adjustment frame) is gone entirely; nothing needs restoring when nothing was touched. All four drawing helpers (`drawArrow`/`drawRect`/`drawCropPreview`/`drawCropHandles`) now take an explicit target context parameter so the identical drawing code produces both the live preview (on `previewCtx`) and the final commit (on `ctx`).
- **New e2e coverage** (17/17, up from 16): a deterministic call-count test (not a timing measurement, which would be flaky and environment-dependent) monkey-patches `CanvasRenderingContext2D.prototype.getImageData` and drags the blur tool through 20 intermediate mousemove steps, asserting the call count doesn't grow at all during the drag and only increases once, at the actual mouseup commit. The clipboard fix's e2e test was rewritten around the new architecture and — for the first time in this saga — asserts genuine success (`"Copied to clipboard."`), not just "reached the expected failure."

## M13 — popup forgets its state on every close/reopen — **done**

- **After a capture, closing the popup (e.g. clicking elsewhere on the page) and reopening it reverted to the pristine "nothing captured yet" state** — report, preview, and the enabled export/copy/annotate buttons all vanished, even though the underlying capture was still fully intact (`background`'s orchestrator state and the image bytes in blob-store both survive independently of any popup). ## M16 — drag tools still laggy after M12, text tool didn't work at all, and a new Select tool to move/resize shapes — **done**

- **User-reported: crop/arrow/rect/blur all still "extremely laggy or non-responsive," and the text tool "does not create a text box."** Two unrelated root causes, plus one new feature request ("a select and edit tool to move and resize arrow, rectangular and textbox").
- **Lag, root cause**: M12 fixed the `getImageData`/`putImageData` CPU-GPU sync stall by moving live previews to a separate overlay canvas (`#previewCanvas`) — but that overlay's own backing buffer was still sized to `canvas`'s full *native* resolution (`previewCanvas.width = canvas.width`), which for a real full-page capture can be tens of millions of pixels. Even pure `clearRect`+shape-primitive draws still made the GPU clear and recomposite a buffer that large on every single `mousemove`, regardless of how cheap the draw calls filling it were — M12 removed the readback stall but not this one. Fixed by sizing `previewCanvas`'s buffer to its own *rendered* CSS box (× `devicePixelRatio`) instead, with a canvas 2D `scale` transform so every existing draw call site keeps working unchanged in `canvas`'s own buffer-space coordinates — only the physical pixels actually pushed to the GPU each frame shrink down to the window's own size. `clearPreview()` now clears using `canvas`'s buffer-space dimensions (the transform maps that onto the smaller real buffer), not `previewCanvas`'s own physical ones.
- **Text tool, root cause #1 (why it silently did nothing)**: `startTextInput` positioned the floating `<input>` at `canvasPoint(e)` (buffer-space, e.g. up to several thousand px) plus `canvas.offsetLeft`/`offsetTop` (CSS-space) — adding two different coordinate spaces together. For any capture wider than the editor window (i.e. almost always, once genuinely scaled down), this placed the input thousands of pixels outside the visible/scrollable area. Fixed by keeping the two spaces separate: `bufferPos` (for where the text actually gets drawn on the canvas) and a proper CSS-space `clientPos` (for where the `<input>` itself gets positioned), computed the same way `canvasPoint`/`pointFromClient` already do it for every other tool.
- **Text tool, root cause #2 (the deeper reason it "did nothing" even once positioned correctly)**: `canvas` isn't a focusable element, so the browser's own default `mousedown` handling blurs whatever currently has focus once the event finishes — including the `<input>` this code had just created and called `.focus()` on, synchronously, before a single frame ever rendered it. The input's own `blur` handler then removed it immediately (empty value → no-op commit). Net effect: the text tool created and destroyed an invisible input on every click, indistinguishable from doing nothing. Fixed with `e.preventDefault()` in the mousedown handler before creating the input — the standard idiom for letting a programmatic `.focus()` call on a non-default target "stick."
- **New Select tool + move/resize, architecture**: arrow/rect/blur/text no longer bake into the canvas the instant they're drawn. Each becomes a `PendingShape` (one at a time — the same simplifying tradeoff the crop marquee above already makes) rendered live on `previewCanvas` with resize handles (reusing crop's existing `handlePositions`/`hitTestHandle`/`resizeRect`/`moveRect`, generic over any `Rect`; arrow gets its own two-endpoint variant, `"start"`/`"end"`, since a line's bounding-box corners aren't its actual endpoints). A new toolbar button/tool (`select`, icon `mouse-pointer-2`) lets the user re-grab an already-drawn shape's handles or body without switching back to the tool that drew it; the tool that drew a shape can also keep adjusting it directly (clicking its handles/body instead of starting a new one). The shape only bakes into the real canvas (`commitPendingShape()` — the only point any of these touch `ctx`'s pixels) when: a different tool is selected (Select is the one exception — that's specifically "keep adjusting"), Enter is pressed, PNG/PDF is downloaded, or the user clicks elsewhere on the canvas while in Select mode. Escape/Delete/Backspace discard it instead. Blur specifically benefits doubly here: its pending preview is a cheap dashed-outline rect (like crop's marquee), not a live pixelated preview, so the expensive `pixelateRegion()` (a real `getImageData`/`putImageData` round-trip) only ever runs once, at the final commit — same principle as the lag fix above, applied to a tool that didn't even have this problem before because it never previewed live in the first place.
- **A same-keystroke event-bubbling bug found while building this**: committing typed text (Enter, inside the floating `<input>`) creates the pending text shape — but that same `keydown` event then bubbles up to the window-level handler that commits *pending shapes*, which (now that one exists) immediately re-baked it in the same tick, before the user ever got a chance to adjust it. Fixed with `e.stopPropagation()` in the input's own keydown handler. Found by screenshotting the intermediate state and noticing the handles that should have been there weren't — not by an initial e2e run, which happened to still pass because the *end result* (text present, in roughly the right place) looked correct either way; only a test asserting the real canvas is *not yet* touched right after Enter (added below) would have caught this on its own.
- **Existing e2e coverage updated, not just left broken**: three existing tests asserted a drag tool's effect landed on the real canvas immediately after `mouseup` — no longer true now that shapes stay pending. Updated each to assert the *pending* (uncommitted) state first, then explicitly commit (Enter) before checking the previously-asserted pixel/call-count outcome — same spirit as how the crop marquee's own tests already worked, just extended to arrow/rect/blur.
- **New e2e coverage** (22/22, up from 19): (1) a structural, non-timing check that `previewCanvas`'s buffer tracks its own rendered size (`× devicePixelRatio`, ±2px rounding) rather than the full capture buffer, for a capture genuinely wider than the editor window; (2) the text tool creates an `<input>` within 20px of the actual click, and the typed result stays *un-baked* until a real commit; (3) the Select tool both moves a pending rect (dragging its body) and resizes one (dragging its `se` handle), each verified by checking the stroke lands at the *new* position/extent and not the original. - **Loading the existing `dist/manifest.json` as a Firefox temporary add-on failed immediately** with `background.service_worker is currently disabled. Add background.scripts.` Root cause: Firefox's stable channel doesn't support the MV3 `background.service_worker` manifest key Chrome requires — Firefox still runs background pages as non-persistent event pages declared via `background.scripts` (an array), not a service worker. This is a manifest-shape difference, not a JS-runtime one: the same compiled `background.js` file works under either loading mechanism, only the manifest key pointing at it differs. Everything else about the extension's actual API usage (tabs, storage, scripting, downloads, runtime messaging) already had a Firefox-compatible surface once the `chrome.*` global itself was abstracted (below), so this turned out to be close to the only hard architectural blocker.
- **`ext`/`captureRateLimit` runtime alias** (`apps/extension/src/platform/webext.ts`): Chrome has no `browser` global; Firefox has had one natively (promise-based, since before Chrome's own promise support) for years. `export const ext: typeof chrome = (globalThis as unknown as { browser?: typeof chrome }).browser ?? chrome;` picks whichever is present at runtime and is typed as `typeof chrome` on both branches, since the WebExtensions surface this extension actually touches is common to both browsers — reusing `@types/chrome`'s shapes avoids a second types package for a near-identical API. ## Publishing automation

**Firefox — done.** `npm run publish:firefox` (`apps/extension/package.json`) builds the Firefox target and runs `web-ext sign --channel=listed`, reading `WEB_EXT_API_KEY`/`WEB_EXT_API_SECRET` from the environment — these come from the operator's own AMO developer account (Developer Hub → "Manage API Keys"), never committed. `.github/workflows/publish-firefox.yml` runs the same command in CI on a `v*` tag push (or manual `workflow_dispatch`), using the same two values stored as GitHub repo secrets, and uploads the signed `.xpi` as a workflow artifact. AMO identifies the add-on across versions by `manifest.firefox.json`'s `browser_specific_settings.gecko.id`, already set — but the *first ever* submission for a new listed add-on still needs one manual pass through the Developer Hub web UI to set listing metadata (description, category, screenshots, privacy policy) that `web-ext sign` has no way to supply; every version after that first one is what this automates. **Not done in this environment**: actually running it — needs the operator's real AMO API key/secret, which don't exist here.

**Chrome Web Store / Edge Add-ons — not started.** Automated submission via `chrome-webstore-upload-cli` (needs a Web Store publisher ID + OAuth client credentials — none of which exist in this environment), Edge-channel e2e matrix, the "capture report" trust-badge toast copy polish, go-to-market test-page expansion. See the original conversation for the full design.

## Known gaps / honest limitations

- `captureVisibleOnly` (visible-area-only capture) hardcodes `dpr=1` for the wasm session rather than reading the real DPR from the page (full-page capture reads it correctly via the content script's `prep` step) — the report's pixel dimensions are still correct either way since those come from the decoded bitmap, but a cosmetic `dpr` field mismatch exists for that one path.
- Service-worker eviction (~30s MV3 idle timeout) drops the cached last-capture session, so "export as PDF" / "copy to clipboard" / "annotate" after a long idle gap requires recapturing — documented in `orchestrator.ts`, not silently broken.
- `wasm-opt` isn't installed in this environment, so the shipped wasm is unoptimized-size (~306KB uncompressed, ~140KB gzipped) — the build script runs it automatically if present, otherwise skips with a warning.
- The annotation editor's undo stack stores full-canvas `ImageData` snapshots (not diffs), capped at 20 steps — fine for the sizes this MVP targets, would need a smarter representation for very large stitched pages.
- The CI workflow's exact commands are all individually verified locally (matching `cargo clippy -D warnings`, `npm ci`, `playwright install --with-deps`, etc.) but the workflow itself has never actually run on GitHub Actions infrastructure — this sandboxed environment has no way to trigger that.
